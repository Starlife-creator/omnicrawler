# 首个任务旅程 · 人工走查清单

> 适用版本：0.12.0 · 对应阶段：第四阶段（完整体验与 UI）· 维护状态：现行

## 这份清单解决什么

`优化方案.md` §二 对第四阶段的验收要求是「**人工完整走查 + 自动回归**」——两份证据，
互不可替代：

| 证据 | 覆盖 | 由谁执行 |
|---|---|---|
| 自动回归 `tests/integration/test_first_task_journey.py` | 数据/状态的**连贯性**：建任务 → 试跑 → 回填解锁 → 运行 → 复核 → 导出，以及"试跑通过后改字段即失效"的运行门禁 | 随 CI / 本地测试自动执行 |
| **本清单（人工走查）** | **真实点击是否可用**、视觉与反馈是否连贯、异常态是否阻断操作、文案是否可理解 | 维护者实机执行 |

自动回归刻意**不经真实点击与子进程**（GUI 的全量运行以子进程调用 CLI，在测试环境脆弱），
所以"点下去会发生什么"必须由人来确认——这正是本清单的存在理由。

## 复用方式（每一轮都照此走）

本清单是**可复用资产**，不是一次性记录。每个候选发布 / 每批体验相关改动之后都这样走一遍：

1. **起环境**（一条命令：固定样本 + 隔离工作区）：

   ```bash
   python tools/walkthrough_env.py
   ```

   它会 ① 建 `<工作区>/{project,data}`，② 起**固定演示站点**，
   ③ 打印种子 URL、期望值、GUI 启动命令（含 `LOCALAPPDATA` 隔离）与结果落盘位置。

   - **样本固定**：列表第 1 页 **6** 条、翻页后合计 **8** 条、附件 **1** 个真 PDF。
     这些数字由 `tools/walkthrough_demo_site.py` 的 `EXPECTED` 提供，
     并由 `tests/unit/tools/test_walkthrough_demo_site.py` 锁住 —— 不会与文档悄悄漂移。
   - **数据隔离**：`LOCALAPPDATA` 指向本次工作区，不碰你的真实数据目录。
   - **项目根**：GUI 用「设置里记住的项目目录」，自动探测是从工作目录向上找含
     `omnicrawler` 的 `pyproject.toml`（在仓库里启动会指向仓库本身）。**请在 GUI 的
     项目选择器里指向 `<工作区>/project`**，并在记录里写明实际项目根。

2. **记三个标识**：应用提交号（`git rev-parse --short HEAD`）、系统与依赖版本、
   本次工作区路径。**没有这三样，跨轮次结论不可比。**

3. **按下面 8 步走**，每步填**判定** + 现象 + 复现路径（表模板见下）。

4. **收口**：可自动化的问题回补测试；纯体验问题进 `优化方案.md` §四.5（见文末）。

5. 工作区可整目录删除。

> **备选**：也可自备目标（本地 HTML 或自建静态服务，例如
> `python -m http.server 8765 --directory <目录>` 后用 `http://127.0.0.1:8765/`）。
> 但那样**期望值要自己定**，且不能与其它轮次直接比较 —— 建议只在排查特定站点问题时用。

## 前置

1. 一台可显示桌面的机器（macOS / Windows / Linux 任一）。
2. 按 `README.md` 安装；启动方式：`python -m omnicrawler.gui`（或 `omnicrawler workbench`，
   打包产物解压后直接运行）。
3. 已用上面的命令起好走查环境（演示站点在跑、工作区已建）。
4. 关闭无关任务，确保观察到的卡顿/报错能归因到本次走查。

## 走查步骤（每步记录"现象"，不只是"通过/失败"）

| # | 环节 | 操作 | 应有现象 | 记录 |
|---|---|---|---|---|
| 0 | **打开** | 启动应用 | 首屏在可接受时间内出现；无空白窗口或报错弹窗；上次的项目/配置被记住 | 启动耗时、首屏状态 |
| 1 | **建任务** | 新建任务，种子里填演示站点的 URL；切换意图/草稿/字段区 | 五个分区可顺序完成；字段规则能添加/删除；无效输入有就地提示而非静默失败 | 哪一步卡住或要猜 |
| 2 | **试跑** | 点「先试跑 N 页」 | 有明确的进行中反馈；结束后给出状态、处理页数、提取记录数；**失败时给出可理解的诊断与下一步建议** | 反馈是否及时、诊断是否可行动 |
| 3 | **试跑回填** | 观察试跑完成后按钮状态 | 「开始全量运行」由不可用变为可用；若改动采集范围或字段，它应**重新变为不可用**并说明原因 | 状态变化是否可见、原因是否说明 |
| 4 | **运行** | 点「开始全量运行」 | 进度、日志、耗时可见；可暂停/停止且**停止后确实停下**（不假死，状态应显示「已取消」而不是「错误」）；运行中界面不冻结 | 停止响应时间、是否假死、终态文案 |
| 5 | **复核** | 运行完成后查看结果表 | 表格能打开且行数与实际一致（**列表任务应含翻页后的合计 8 条**）；可筛选/翻页；点某行能看到证据（选择器/来源）；大数据量下不卡死 | 行数、翻页、证据可见性 |
| 6 | **导出** | 触发导出（自动或手动） | 生成 Markdown 交付物且内容完整（含字段名与记录）；导出失败有明确提示，不静默丢弃 | 产物路径、内容是否完整 |
| 7 | **附件/OCR** | 把演示站点的附件 URL（`/files/contract.pdf`）加入下载或 PDF 流程 | 附件能取到；PDF 流程能给出**字段来源位置与不确定性**；需要复核的进复核队列而不是被当成正常结果 | 附件是否取到、不确定性是否可见 |
| 8 | **异常态** | 故意制造：URL 不可达 / 目标文件被删 / 中途停止 | 三态（空/加载/错误）视觉可区分；错误不伪装成"没有数据"；用户能从提示中找到下一步 | 是否误导、是否有出路 |

## 与自动回归的关系

自动回归锁定**流程不断**（数据与状态能在环节间传递）；本清单锁定**体验可用**（人能否顺畅走完）。
只做前者会漏掉"能跑但难用"，只做后者会漏掉"改一处就悄悄断了流程"。

走查发现的每个问题按两类处理：
- **可自动化的** → 回补到 `tests/integration/test_first_task_journey.py`（或对应视图测试），
  避免下次再靠人发现；
- **纯体验/视觉问题** → 记入 `优化方案.md` §四.5（用户体验与 UI）的待办，
  按「用户影响 / 发生场景 / 改动风险」排序。
