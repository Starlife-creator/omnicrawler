## 1. 目标、原则与范围

本轮目标是让用户可靠完成“输入 → 转换/采集 → 检查结果 → 取消或恢复 → 交付”，并在保留现有能力的前提下降低大文件资源消耗和维护成本。

排序依据：用户影响、证据强度、发生场景、改动风险和维护成本；不以文件行数、测试数量或抽象层数量作为优化成效。

约束：

- 保留配置协议 v5、现有 CLI 入口、Reader/Writer 注册机制和可选依赖边界。
- 容错跳过继续可用，但缺失、截断和类型转换必须可解释。
- 后台任务取消、文件提交和窗口关闭使用明确的生命周期契约。
- 小文件保持简单路径；大文件逐路径改善，不承诺所有格式恒定内存。
- 基准先记录再设阈值；已有质量门禁继续执行，不凭机器波动增加误报。
- 本轮不引入分布式重构、新数据库后端、强制 Arrow 依赖或全面 GUI 重写。
- 固定的是 CI 验证输入，不冻结用户使用的在线市场，不弱化市场签名、防回放和权限检查。

### 1.1 实施收敛规则

核心收益以结果正确可解释、取消行为真实、旧输出受保护和已证实的大文件资源改善为准。不承诺所有性能指标同时改善或风险为零；减少重写与长期分支可以降低维护成本，但吞吐、内存、磁盘之间仍需实测取舍。

- 先复用现有 `ConvertResult.warnings/extra`、`ProgressTracker.cancel()`、注册机制和临时文件写入惯例；仅在现有能力确实不足时增加小型内部实现。
- 新增机制必须解决当前调用路径上的具体问题。首期不建设通用统计框架、全局任务状态机、可插拔事务框架、通用能力注册中心或全局锁管理器。
- 对外保留兼容入口，对内尽量只保留一套实现。例如旧的列表读取入口可以包装同一迭代读取内核，不维护两份解析逻辑。
- 首期不增加用户需要理解的执行引擎开关、新严格结果模式或自动分 sheet 策略。继续使用既有 `on_error`，把结果说明做好。
- 正确性修复与性能替换、GUI 重构分开审查。每项完成后先确认收益，再启动下一项，不把路线图当成必须全部执行的清单。
- 每个变更新增的接口、配置、依赖、兼容分支均需有当前使用者和存在理由；过渡代码须有明确移除条件，不能无限保留。
- 完成标准包含删除被替代的内置重复实现和过期测试分支；不能把更多文件或更少单文件行数当成完成指标。
- 无法证明收益、需要扩大公共接口才能完成的小优化、明显增加磁盘开销且无用户场景支持的路径，暂停或缩小范围。

## 3. 第一阶段：转换结果可信、取消有效、输出安全

### 3.1 统一转换统计与结果展示

复用 `ConvertResult.warnings/extra` 传递结果，不先新增公共统计协议。首期只补现有内置路径能够准确得到的已解析、实际写入、跳过和截断数量，以及有限错误位置；内部最多使用一个小型统计容器，直接字段足够时无需新建类。以下表格是口径定义，按已实现路径提供，不要求首期建设完整统计子系统。

表格记录转换统计口径（按当前路径需要选用）：

| 字段 | 定义 |
|---|---|
| input_units | 已观察到的输入逻辑单元数；CSV 不使用物理换行数代替记录数 |
| ignored_units | 空白行等按格式约定忽略的单元数 |
| rejected_units | 无效 JSON、非对象 JSON、不合法记录等被拒绝的单元数 |
| accepted_records | 成功解析、进入转换阶段的记录数 |
| written_records | 已提交到目标文件的记录数；失败/取消前写入临时文件不能算已交付 |
| omitted_records | 达到输出上限等原因未交付的有效记录数 |
| transformed_values | 发生截断、类型强制转换等有损处理的值数及分类 |
| issue_counts / samples | 按错误码统计的数量、有限的定位样例 |

单记录对单记录路径验证 `accepted_records = written_records + omitted_records`（成功提交时）；输入计数按格式明确表头和空行规则。文档转文本、聚合等路径使用独立单位定义，不硬套表格等式。未知计数使用 null/未知，不伪造零或估算为精确值。

兼容措施：

1. 暂保留现有 `ConvertResult.rows` 的历史口径，文档明确；GUI、CLI 的用户摘要优先读取新增的实际写入数。
2. 如后续统一 rows 语义，单独做调用方审计、兼容公告和版本化变更，不在性能重构中隐式改变。
3. 保留 `on_error=skip|abort` 默认行为；skip 返回完整计数，abort 返回定位明确的错误且不覆盖旧输出。
4. 对非对象 JSON 等结构错误统一定义策略，避免 abort 模式仍无说明地忽略。
5. 内置 Reader 通过既有 options 接收每次转换独立的可选统计容器；不改变注册签名。自定义 Reader 不提供计数时保留未知语义，不为此新增插件统计能力协商层。
6. 保持原有 warnings 字段，汇总 Reader 和 Writer 问题；错误样例数量、文本长度设上限，默认只存位置与原因，不复制完整原始记录或凭据。
7. 同步两个命令行入口及 GUI，普通用户看到“写入 98 条，跳过 2 条，可查看原因”；详细字段不直接堆在主界面。
8. 默认容错成功的 CLI 退出码保持兼容；复用 `on_error=abort` 处理现有解析错误，不新增严格结果模式。若以后有明确的“拒绝任何有损输出”需求，再单独设计提交前策略，不能把所有警告一律当失败。

XLSX 特别处理：项目当前 1,000,000 条限制是应用策略，不能称为 Excel 精确硬上限。保留首期限制，修正文案，报告实际写入/省略数；单元格截断同样计数。多 sheet 自动拆分不作为首期默认行为，以免改变下游读取契约。

验收：正常数据、坏行、空行、非对象 JSON、CSV 引号内换行、XLSX 行数/单元格边界均能核对；三行最小复现显示“写入 2 条，跳过 1 条”；所有入口结果一致；错误样例数量有界。

### 3.2 统一输出提交边界

在取消改造前明确输出生命周期。先补 XLSX 的临时写入缺口，沿用其他文件 Writer 的既有方式；相同的临时创建、关闭、替换与清理代码确有重复时提取一个内部辅助函数/上下文管理器，不新增通用输出会话或事务框架。现有 `atomic_write(path, bytes)` 需要完整 bytes，不为复用它而重新整文件加载。

1. 文件型输出在目标目录创建本次转换独占的临时路径；保留格式后缀，避免依赖扩展名的 Writer 失效。
2. 完成写入并关闭文件和数据库句柄，核对写入过程的统计后再提交；格式完整性重读主要放在测试中，运行时仅做必要的轻量校验，不默认全文件二次读取。
3. 用同文件系统替换完成提交；提交前失败或取消保留原目标；只清理本次任务拥有的临时文件。
4. XLSX 保存走临时路径，不再直接保存到最终目标；回归测试在句柄关闭后重新打开核对内容。
5. DuckDB 先确认既有目标的更新语义：若需保留其他表，使用事务或备份副本更新，不能把整个数据库作为新文件盲目替换。
6. 临时路径逐任务唯一，避免任务互相删除临时文件。复用 GUI 现有运行中禁用逻辑；若同进程确有多个入口可写同目标，才增加局部冲突检查，不建设跨进程全局锁管理器，也不声称能阻止所有外部进程覆盖。覆盖确认以现有交互授权为准。
7. 提交失败（目标被 Excel 占用、磁盘满等）显示明确原因，原文件保持可用。清理失败记诊断，不反向伪造成功状态。

此保证针对进程内失败、正常取消和文件替换边界；不宣称仅靠 rename 即实现所有平台上的断电持久性。自定义 Writer 如不能支持事务输出，须如实声明能力；文档及实现不能把它包装成已经具备完整保证。

验收：每种已支持安全提交的内置 Writer 均验证正常输出、写入中途失败、提交失败、已有目标保护与临时文件清理；DuckDB 同时验证非目标表保留。

### 3.3 贯通取消与生命周期

拟议方案：`convert(..., should_stop=None)` 可选检查回调；GUI 使用标准库 `threading.Event` 及其 `is_set`，不额外建设取消令牌体系；内部用专用 `ConversionCancelledError` 区分取消和失败。复用 `ProgressTracker.cancel()`，GUI/CLI 在边界映射为 cancelled。提交竞态如需同步，仅在本次任务的取消/提交边界设置必要同步，不扩展成通用调度器。

- 检查位置：启动前、逐批读写、昂贵处理前后、最终提交前。
- 取消不通过进度回调异常传播；现有回调错误隔离策略继续保留。
- Worker.cancel() 设置事件；两个 Worker 都接入同一取消约定；进度、成功、失败、取消有明确终态映射。
- 每次任务只发一个业务终态；QThread.finished 负责清理引用，不代表业务成功。
- 将“取消请求”和“进入提交”排序为明确同步边界：先被接受的取消阻止提交；提交已开始则等提交完成并报告真实结果，不能已覆盖文件却显示取消。
- 停止请求发出后按钮显示“正在停止”，不提前显示“已取消”；停止后才能重新运行。
- 窗口关闭先取消，延后销毁持有运行中线程的页面；禁止用 QThread.terminate() 强制终止作为默认方案。
- 对单次第三方解析/打包调用无法中断的路径，标明“等待当前操作结束”；不承诺统一的秒级中断。仅当实测阻塞严重时，再评估进程隔离。
- CLI Ctrl+C 进入取消/清理流程；复用或明确记录项目退出码约定，避免把取消显示为一般错误堆栈。

状态路径：running → cancelling → cancelled，或 running → committing → finished；异常进入 failed。有警告的完成使用 finished 加质量摘要，不随意扩展公共进度状态枚举。

验收：开始前、读中、写中、提交前、提交期间分别注入取消；取消后的旧文件保护、一次终态、线程回收、再次运行均可验证。项目可控的分批循环以受控机器上取消响应 P95 ≤ 1 秒作为初始目标，第三方不可中断调用单独列报。

## 4. 第二阶段：验证输入可复现、建立用户场景基线

### 4.1 固定 CI 市场版本并保留最新兼容验证

- 使用单一市场 SHA 配置；优先采用一个文本文件或现有配置位置，多个工作流共同读取，不为单个 SHA 建设版本管理服务。
- PR 与发布验证读取同一描述文件；保留市场仓库在主仓库同级的布局。
- 获取指定提交并验证实际 HEAD 相等；未取得指定版本即失败，不静默退回 main。
- 最新市场验证复用同一组跨仓库契约测试，仅改变输入 ref，不复制完整 CI 矩阵。先提供手动触发并纳入市场兼容变更验收；有实际频率需求再增加定时运行。解析出的 SHA 随报告保存，失败进入兼容问题处理流程。
- 更新市场锁定版本通过明确变更，附兼容测试结果；生态协议变更时必须同步更新，不机械定期追新。
- 单元测试尽量使用自包含 fixture；只有跨仓库契约测试依赖市场快照，降低无关测试与外库的耦合。
- 历史签名目录可能包含时效或序列约束：单元 fixture 控制时钟，生产验证仍使用真实规则，不以“可复现”为由关闭校验。
- 记录应用 SHA、市场 SHA、Python/依赖环境及平台；固定一个仓库版本不等于整个构建逐字节可复现。
- 保持现有 token 权限边界，避免在日志和报告中保存带凭据的仓库地址。

验收：同一应用/市场组合重跑能定位相同输入；故意指定不存在 SHA 必须失败；跨仓库集成测试仍真正执行；仅 clone 主仓库的核心测试能力与当前约定一致。

### 4.2 建立代表性基准

复用已有基准设施，新增少量用户任务负载。基准生成器使用合成数据，不使用真实用户数据。

| 场景 | 规模与边界 | 指标 |
|---|---|---|
| CSV → JSONL | 1 万 / 10 万 / 100 万条，固定列宽；另测长字段与多行 CSV | 峰值 RSS、用时、输出正确性 |
| JSONL → CSV | 同规模；尾部新列、嵌套字段、坏行 | 内存、磁盘暂存、列序、错误统计 |
| 表格 → XLSX | 典型规模及接近应用上限；文件被占用 | RSS、实际写入数、提交结果 |
| 取消 | 读取/写入/提交边界及文档解析 | 请求到终态时延、残留线程/文件 |
| GUI 首次成功 | 本地静态 fixture；简单模式输入到三页试跑结果 | 可交互时间、完成耗时、阻断问题 |
| 恢复与交付 | 临时网络错误、任务中断、目标不可写 | 数据完整性、错误建议、恢复结果 |

每个性能样本独立进程运行；记录 Python、OS、依赖、CPU/RAM、样本参数和执行路径。冷启动和热运行分开；RSS 包括 Python 与原生库，tracemalloc 只能作为补充。小文件用于发现流式路径额外开销。

CI 首期上传报告，不采用统一“慢 10% 就失败”。确定性行为与结果正确性立即作为门禁；耗时先做重复测量和噪声分析。有稳定基线后，同环境比较，并对明显回归复测。内存阈值由基线与目标设备预算确定，不提前虚构 MB 数字。

## 5. 第三阶段：分路径实现有界资源转换

### 5.1 保留旧接口，增加流式能力

- 保留 `READERS`、`WRITERS`、直接 read_* 返回列表的兼容行为。
- 内置读取先抽出单一迭代内核，旧 read_* 入口以 list(...) 包装保证兼容；转换路径直接消费同一内核。不另建一套解析引擎或通用能力注册中心。
- 只在内置实现仍为实际注册对象且路径已验证时启用对应迭代路径；用户注册覆盖始终优先，沿用既有自定义实现。不支持流式的路径不称为有界内存。
- `convert()` 在内部选择已验证路径，不新增长期 legacy 引擎开关；回归验证通过后删除被替代的内置解析代码，保留薄的兼容入口。
- 分批以行数和估算字节双约束；单条超大记录另设边界，明确拒绝/警告策略。只固定行数不能保证内存上限。
- 不将 Arrow、DuckDB 或其他大依赖加入基础安装；使用它们的路径继续按现有 extras 探测能力。

### 5.2 转换路径与字段语义

| 路径 | 方案 | 必须保留或明确的语义 |
|---|---|---|
| CSV → JSONL | 表头确定结构，逐批解析、逐批写出 | 编码、空值、列名、多行字段、嵌套输出 |
| JSONL → JSONL | 逐条验证/展开/组装 | flatten/nested、证据字段、坏行策略 |
| JSONL → CSV | 完整发现列；临时规范化暂存后写出，或验证输入稳定的两遍扫描 | 基础列 → 指定优先列 → 首次出现列，末尾新列不丢失 |
| CSV/JSONL → XLSX | 完整列计划加 write-only 工作簿 | 表头样式、冻结窗格、实际写入计数、行及单元格限制 |
| Parquet | 批次读取和写入，显式类型计划 | 空列、混合类型、精度、结构变化；不静默损失类型 |
| DuckDB | 批次读取，事务/安全副本写入 | 表名校验、列类型、既有库其他表、幂等及失败边界 |
| 文档 → 文本/Markdown | 保留独立解析路径，先补统计与取消边界 | 不以一条记录假设文档解析内存有界 |

动态结构处理要求：

1. 未知字段不得仅因首批没出现而静默丢弃。
2. JSONL 的临时规范化表示必须保留现有值语义；不能为复用临时格式而把时间、二进制、Decimal 等值强制字符串化。类型丰富来源单独设计暂存方案。
3. 两遍扫描需要检查输入未改变；文件大小/mtime 检查只能作为弱检测。严格一致场景使用稳定副本或有内容校验的暂存，发现变化拒绝提交。
4. 自动编码先做有限采样，再以严格解码完成读取；后段解码失败明确报告或从头按兼容策略重试，不用替换字符掩盖问题。不得恢复整文件 read_bytes 作为大文件隐式后备。
5. 类型推断要有空值、混合类型和后期变化策略；Arrow 首块冻结类型的限制必须纳入设计。保持原始类型或明确报告有损转换。
6. 临时空间有配额和清理所有权，空间不足明确失败；不把内存问题变成无上限的磁盘占用。
7. 大文件进度展示已处理数量/字节及估计状态；分阶段扫描、写入、提交的进度不倒退，未知总数不伪造精确百分比。

验收：在独立基线版本与候选版本上比较同一数据的逻辑记录、列顺序、类型、统计和结果，不为对比而在生产包永久保留两套解析器；在固定列宽、最大记录长度及列数的样本上，10 倍记录规模不应导致数据缓冲内存近似 10 倍增长。总 RSS 与原生库开销分别分析，不把单次测量当成普遍结论。

首批仅启用 CSV/JSONL 已通过对等验证的路径，再按测量结果决定 XLSX 和 Parquet/DuckDB。小文件若有明显性能回退，先优化同一内核的缓冲策略；只有证明必要才增加局部批量分支，不复制整个转换实现。

## 6. 第四阶段：按职责改善 GUI 边界

先处理插件启停业务流程，后处理转换控制器与关闭协调；背景绘制、样式等低影响职责随功能修改整理。

- MainWindow 保留组合、连接信号和导航；应用服务负责插件验证、兼容检查、授权绑定检查和配置变更。
- 服务返回普通 DTO，不返回 Qt 控件、数据库连接等实现对象。
- UI 展示待授权版本、载荷、作者、权限；用户确认后服务重新验证待启用对象与已确认摘要一致，避免确认期间文件变化。
- 已有权限失效、签名、版本绑定和启用失败回退语义全部保留。
- 控制器定义显式输入、输出、状态所有权；不要让新委托继续依赖主窗口大量私有属性，形成“只搬文件”的重构。
- Qt 对象的 parent、线程归属和销毁责任写清楚；关闭协调只管理资源生命周期，不混入业务提交逻辑。
- 原子业务步骤及权限边界通过服务级测试验证，GUI 测试覆盖信号、确认与关闭行为。

验收：插件启用/更新失效/拒绝授权/验证失败行为不变；服务可无 QApplication 测试；架构检查无新增非必要依赖环；修改一个业务规则不要求更改无关窗口代码。主窗口减少多少行不是验收指标。

## 7. 条件性优化：复核队列与数据库

前置条件：找到真实调用入口和工作负载，或明确计划将该方法接入用户流程。当前未满足前不迁移 schema。

满足条件后：

1. 使用 EXPLAIN QUERY PLAN 与不同 run 大小、待复核比例测量查询；区分 run_id 索引筛选与 JSON 文本扫描开销。
2. 若证明确有瓶颈，增加结构化待复核字段与匹配过滤/排序的索引；优先分页 API，旧完整列表接口保留兼容。
3. 明确所有更新路径：采集、质量重算、人工修改、恢复、旧记录导入；新字段是受维护的派生状态，不能与 evidence 漂移。
4. 迁移前备份，分批回填、可续跑、校验新旧结果一致；新增列优先于破坏性替换。
5. 游标使用稳定唯一排序键，限定 run/filter；说明动态结果集一致性。若要求无遗漏无重复，使用快照语义，而不是仅声称 keyset 分页天然保证。
6. 分页读取缩短持锁时间；用稀疏命中、连续修改、跨 run 场景验证结果与性能。

## 8. 用户旅程与验收矩阵

| 旅程 | 验收结果 | 验证方式 |
|---|---|---|
| 第一次采集 | 简单模式第一页可补齐必需信息，试跑三页后能打开并理解结果 | 本地站点 fixture + 人工桌面走查 |
| 普通文件转换 | 列、类型、记录数符合契约，输出可重新打开 | 对等集成测试 |
| 含坏行转换 | 用户看见写入/跳过数和原因；既有 abort 模式保护旧文件 | CLI + GUI 摘要测试 |
| 大文件转换 | 内存、暂存与进度可解释，尾部新增列不丢 | 独立进程基准 + 内容核对 |
| 取消或关闭 | 一次终态，旧输出安全，无运行中线程被销毁 | 确定性事件同步 + 桌面测试 |
| 输出被占用 | 显示可执行修复建议，释放占用后可重试 | Windows 文件占用场景 |
| 中断恢复 | 已提交成果与待执行状态可区分，无额外数据遗漏 | 复用现有恢复 E2E，按发现补充 |
| 插件启用 | 所批权限与实际版本/载荷一致，失败可理解 | 服务契约 + GUI 集成 |

同一场景优先复用已有测试，不复制一套平行测试体系。取消时序使用事件/屏障控制，不依赖任意 sleep。人工桌面走查与 offscreen 自动测试分别报告，不相互替代。

## 10. 验证、上线与回退

每包先跑针对性测试和受影响契约；跨模块里程碑运行仓库既有 lint、类型、架构、最小安装与相关集成门禁。准备发布时执行现有跨平台/构件完整性流程，避免每个小改动重复跑全部重型矩阵。

重点测试目录为现有 `tests/unit/convertx/`、`tests/unit/services/`、`tests/gui/` 和相关 CLI/E2E；根据实际组织新增测试，不把拟议文件名当作已经存在的路径。

发布策略：

1. 完成状态和计数修复先交付；进度协议、结果 JSON 增量变更记录兼容性。
2. 流式路径逐格式、逐独立变更启用，正确性修复与性能替换分开提交；回退通过撤回对应性能变更完成，不为回退永久保留旧解析引擎。发现不支持的语义在提交前失败，不能在写入一半后悄悄换引擎。
3. 重跑回退路径必须显式处理输入稳定性、临时输出和取消状态；不能吞掉真实数据异常自动重试。
4. 回退某条流式路径时，仍保留统计、取消和安全提交修复，不退回已知缺陷；性能变更上线前验证这种回退可独立执行。
5. 市场版本描述文件独立回退，不修改在线市场和用户信任缓存。
6. 数据库优化若实施，优先允许旧代码忽略新增列；确认旧版本兼容性，不以删除用户库实现回退。
7. 成果报告列出应用/市场 SHA、依赖环境、通过的路径、已知限制和未运行的验证；没有压测就不写性能提升百分比。

本轮整体完成标准：

- 三行坏行示例和取消缺口关闭，XLSX 统计及提交行为一致。
- 已启用流式路径的数据语义对等、资源边界有测量证据。
- CI 市场输入可追溯，最新市场兼容性仍可发现。
- 至少完成上述用户旅程的代表性验收，明确自动化与人工验证边界。
- 未满足条件的数据库迁移明确留后续，不以“方案完整”为由盲目实施。

### 10.1 每项变更的收益与复杂度验收

每个工作包在合并前回答以下问题，并把答案简要写入变更说明，而非另建审核系统：

1. 哪个实际输入或操作变好了？提供结果对比或针对性复现。
2. 是否改变字段、列序、类型、取消终态或旧输出？若改变，必须是已说明的缺陷修复或显式兼容决策。
3. 增加了哪些长期接口、配置、依赖或执行分支？现有机制为什么不足？
4. 被替代的代码是否删除？保留的是必要的调用兼容入口还是重复业务逻辑？
5. 耗时、内存、磁盘、维护复杂度中，哪些改善、哪些变差？没有测量的数据明确留空。
6. 若收益不成立，能否只撤回这一项而保留已完成修复？

正确性和数据语义不能用性能收益抵换。内存下降但磁盘或耗时明显恶化时，仅在目标场景确实需要且代价可接受时采用；不宣称所有收益不变。GUI 与数据库优化没有真实收益证据时停在分析阶段。上述条目用于限制设计膨胀，不要求固定文件数、类数或覆盖率增量。

## 11. 外部借鉴及适用边界

- [Apache Arrow：CSV 增量读写](https://arrow.apache.org/docs/python/csv.html#incremental-reading)：借鉴批次处理；注意类型首块冻结等约束，不作为强制依赖或通用加速承诺。
- [SQLite：LIKE 优化约束](https://www.sqlite.org/optoverview.html#the_like_optimization)：前置通配符不满足普通 LIKE 范围优化；仍需结合 run_id 等实际索引分析。
- [SQLite：EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html)：先验证真实查询计划，再决定索引及 schema 变更。
- [Qt：线程与 QObject](https://doc.qt.io/qt-6/threads-qobject.html)：遵循对象线程归属、事件循环和销毁规则；取消必须由业务协作实现。
- [GitHub actions/checkout](https://github.com/actions/checkout#usage)：支持精确 ref/SHA；实际采用方式需保持项目双仓库布局。
- [pyperf：运行基准](https://pyperf.readthedocs.io/en/latest/run_benchmark.html)：重视重复样本、稳定性与环境噪声；不将共享 runner 的一次耗时变化直接视为回归。

这些资料用于约束设计，不替代项目本地性能测量、兼容测试和用户旅程验证。
